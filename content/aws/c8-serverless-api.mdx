Time to put the pieces together into something real: a small web API for notes. You'll be able to save a note and list notes with plain HTTP requests, and there won't be a single server to look after.

```
curl  ->  API Gateway  ->  Lambda  ->  DynamoDB
```

- **API Gateway** gives your function a public HTTPS address.
- **Lambda** runs your code for each request.
- **DynamoDB** stores the notes.

Along the way, you'll meet the two permission problems almost everyone hits the first time. Expect a 500 error or two: reading the logs to fix them *is* the lesson.

## The table

<Cmd>aws dynamodb create-table --table-name Notes --attribute-definitions AttributeName=id,AttributeType=S --key-schema AttributeName=id,KeyType=HASH --billing-mode PAY_PER_REQUEST</Cmd>

<Cmd>aws dynamodb wait table-exists --table-name Notes</Cmd>

## The role

Same as lesson C7: a role Lambda can take on, with permission to write logs.

<Cmd>{`echo '{"Version":"2012-10-17","Statement":[{"Effect":"Allow","Principal":{"Service":"lambda.amazonaws.com"},"Action":"sts:AssumeRole"}]}' > trust.json`}</Cmd>

<Cmd>aws iam create-role --role-name notes-role --assume-role-policy-document file://trust.json</Cmd>

<Cmd>aws iam attach-role-policy --role-name notes-role --policy-arn arn:aws:iam::aws:policy/service-role/AWSLambdaBasicExecutionRole</Cmd>

## The code

Your function talks to DynamoDB with the **AWS SDK for JavaScript v3**, which Lambda's Node.js runtime includes. The **document client** (`lib-dynamodb`) lets you use plain JavaScript objects instead of typed `{"S": ...}` values. API Gateway sends each HTTP request as an event: the method is in `event.requestContext.http.method`, and the request body is a string in `event.body`.

<Cmd>edit index.mjs</Cmd>

Paste this into the Files tab:

```
import { DynamoDBClient } from "@aws-sdk/client-dynamodb";
import { DynamoDBDocumentClient, PutCommand, ScanCommand } from "@aws-sdk/lib-dynamodb";

const db = DynamoDBDocumentClient.from(new DynamoDBClient({}));

export const handler = async (event) => {
  if (event.requestContext.http.method === "POST") {
    const note = JSON.parse(event.body);
    await db.send(new PutCommand({ TableName: "Notes", Item: note }));
    return { statusCode: 201, body: JSON.stringify({ saved: note.id }) };
  }
  const { Items } = await db.send(new ScanCommand({ TableName: "Notes" }));
  return { statusCode: 200, body: JSON.stringify(Items) };
};
```

The client is created **outside** the handler, so it's set up once per copy of the function and reused by every request, not rebuilt each time. (A scan is fine for a handful of notes. Lesson C6 explains why a big table would need a better key design.)

<Cmd>zip function.zip index.mjs</Cmd>

<Cmd>aws lambda create-function --function-name notes --runtime nodejs20.x --handler index.handler --role arn:aws:iam::123456789012:role/notes-role --zip-file fileb://function.zip</Cmd>

<Cmd>aws lambda wait function-active-v2 --function-name notes</Cmd>

## The API

An **HTTP API** with a `--target` sends every request to one function:

<Cmd>API=$(aws apigatewayv2 create-api --name notes-api --protocol-type HTTP --target arn:aws:lambda:ap-south-1:123456789012:function:notes --query ApiId --output text)</Cmd>

<Cmd>curl https://$API.execute-api.ap-south-1.amazonaws.com/notes</Cmd>

`{"message":"Internal Server Error"}`. The function didn't even run: check `aws logs tail /aws/lambda/notes` and there's nothing new. **Problem one:** a function's own resource policy must allow API Gateway to call it. Add that permission, limited to this API:

<Cmd>aws lambda add-permission --function-name notes --statement-id apigw --action lambda:InvokeFunction --principal apigateway.amazonaws.com --source-arn "arn:aws:execute-api:ap-south-1:123456789012:$API/*"</Cmd>

Now save a note:

<Cmd>{`curl -X POST https://$API.execute-api.ap-south-1.amazonaws.com/notes -d '{"id":"n1","text":"buy milk"}'`}</Cmd>

Still a 500. This time the function *did* run. Read why:

<Cmd>aws logs tail /aws/lambda/notes</Cmd>

**Problem two:** `AccessDeniedException ... not authorized to perform: dynamodb:PutItem`. The role can write logs, but nothing allows it to touch the table.

## Least privilege, for real

You could attach `AmazonDynamoDBFullAccess`, and it would work. It would also let a bug or an attacker delete every table in the account. Instead, allow exactly the two actions this function uses, on exactly this table:

<Cmd>{`aws iam put-role-policy --role-name notes-role --policy-name notes-table --policy-document '{"Version":"2012-10-17","Statement":[{"Effect":"Allow","Action":["dynamodb:PutItem","dynamodb:Scan"],"Resource":"arn:aws:dynamodb:ap-south-1:123456789012:table/Notes"}]}'`}</Cmd>

<Cmd>{`curl -X POST https://$API.execute-api.ap-south-1.amazonaws.com/notes -d '{"id":"n1","text":"buy milk"}'`}</Cmd>

<Cmd>curl https://$API.execute-api.ap-south-1.amazonaws.com/notes</Cmd>

`{"saved":"n1"}`, then your note in a list. You have a working serverless API. Look at the resources panel: one table, one function, one role, one API, and nothing that needs patching, scaling or restarting. If a million people used it tomorrow, API Gateway and Lambda would add copies on their own, and DynamoDB on-demand would keep up. That's the appeal of serverless. The trade-offs are cold starts, per-request pricing that can cost more than a busy server at very high steady traffic, and more pieces to wire together, as you've just seen.

## What to remember

- API Gateway, Lambda and DynamoDB make a complete backend with no servers.
- Two permissions are needed: the function's resource policy lets API Gateway call it, and the role lets the function use the table.
- A 500 with no log means the function never ran; a 500 with a log means read the log.
- Grant exact actions on exact resources, not full access.
